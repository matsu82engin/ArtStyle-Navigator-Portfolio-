## ■ 作成背景
私は以前漫画家を目指していたのですが、目指し始めた時は絵が上手くありませんでした。<br>

もちろんうまくなるように努力はするのですが、"どういう風な絵で上手くなりたいのか" ということが、教材やどんな情報サイトにもあまり載っていなかったのを記憶しています。<br>
絵の描き方は人によって違うので、絵を描くのは上手くなったけれど自分の描く絵が自分は好きじゃない、という不思議な現象が身近でしばしば起きていたことがあります。<br>

その現象を少しでも解消し、自分が求める絵柄を探して、その絵柄の描き方や他の人が行っているコツの情報を共有したりする、<br>
絵が上手くなりたい人に向けたアプリケーションを作れたらいいのでは考え、このアプリケーションを作成したいと考えました。


## ■目的
- 絵が上手くなりたい人が、自分の好きな絵で上手くなれるような情報が見れる。
- 自分の絵柄の他の描き方や道具の情報を共有する。
- コツや情報を知ることで、絵を描くモチベーションが上がる


## ■ターゲット
- 自分の好きな絵柄を見つけ、その絵柄で上手くなりたい人
- 自分と同じような絵柄で他の人の描き方やコツを知りたい人
- 他の人がどんな画材道具を使っているか知りたい人


## ■メリット
- 自分の好きな絵で努力ができるようになる。
- その人しか知らないおすすめの描き方のコツや情報が見れる。


## ■工夫した点・技術的な意思決定
**Nuxt（SSR）と devise_token_auth の組み合わせによるリロード時の認証エラー**

### 【原因】
Nuxtの auth モジュールは、リロード時に fetchUser を実行してRails側へユーザー情報を問い合わせます。<br> 
しかし、SSRのリロード直後は処理がブラウザではなく「Nuxtのサーバー（Node.js）」上で実行されます。<br>
そのため、ブラウザの document.cookie を参照する実装では、SSR時のNode.js環境からCookieを取得できず、<br>
Railsが求める認証ヘッダー（access-token や client など）を空のままリクエストを送ってしまうことが原因でした。

### 【試したことと失敗した理由】 
この課題に対して、大きく2つのアプローチを試しました。
1. Axiosのインターセプターでヘッダーを自動付与する
  - js-cookie を使ってリクエスト直前にトークンを差し込もうとしました。
  - 結果： js-cookie は内部でブラウザの **document.cookie を参照する仕組み**です。<br>SSR時（Node.js上）には document オブジェクト自体が存在しないため、Cookieが取得できずヘッダーが空のままとなり、失敗しました。
2. vuex-persistedstate で localStorage からVuexへ復元する
  - トークンを localStorage に保持し、Vuexストアへ復元してヘッダーに載せる方法を試しました。
  - 結果： localStorage もブラウザ専用の領域であるためサーバー上からは参照できません。<br>
  また、Vuexが復元されるタイミングよりも前に auth モジュールの fetchUser がRailsへリクエストを送ってしまうため、タイミング的にも間に合わず失敗しました。

### 【判断】 
原因を掘り下げた結果、本質的な問題は以下の２点だとわかりました。<br>
1. リロード時は documentオブジェクトが存在しないので、Cookies.get ができない。(Cookie にアクセスできない)
2. localStorage や Vuex を使おうとしても、SSR時の処理はNode.js上で実行されるため、<br>ブラウザ専用APIである localStorage を利用できず、Vuex の復元は遅いため認証情報の取得がそもそもできない

SSRのまま解決するには、サーバー側でHTTPリクエストからCookieを解析・引き継ぐような複雑な実装が必要になります。<br>
しかし、今後の保守性・学習コストを天秤にかけた結果、認証方式を崩すのではなく、最初からすべての処理がブラウザ上で完結するSPA構成へ切り替える判断をしました。

SPA構成にすることで認証処理をブラウザ側で実行できるようになり、document.cookie や localStorage から認証情報を取得して、必要な認証ヘッダーを付与できるようになり、無事に認証エラーを解消できました。

### 【学び】 
この経験から、単にエラーメッセージを検索して対処するだけでなく、
「プログラムがどの実行環境（Node.jsかブラウザか）で動いているのか」や「フレームワークのライフサイクル」を意識し、<br>仕様と実装コストのバランスを踏まえて技術構成を選択する重要性を学びました。

## ■認証設計について(トークン管理の見直し)
Nuxt と Rails（devise_token_auth）で認証機能を構築しました。<br>
開発途中でトークン管理の仕様を誤解しており、後から気づいて現在リファクタリング中です。

### 【当初の実装】 
devise_token_auth は config.change_headers_on_each_request = true によりリクエストごとにアクセストークンを更新するため、本来リフレッシュトークンの概念がありません。<br>
この仕様を知らずにJWTでリフレッシュトークンを自作しており、
後から気づいた際、せっかく作った機能を活かす方向で change_headers_on_each_request を false にし、<br>
「アクセストークン失効直前にリフレッシュトークンで更新する」独自方式に落とし込みました。

### 【実装後に認識した課題】 
・アクセストークンとリフレッシュトークンの有効期限を同等にしたため、本来の「短寿命化による漏洩リスクを小さくする」を活かせていない<br>
・リフレッシュトークンの値をレスポンスのJSONボディにも含めていたため、vuex-persistedstate 経由で LocalStorage にも重複保持されており、XSS 耐性の観点で改善が必要

### 【現在進めているリファクタリング】
独自のリフレッシュトークン機構を撤去し、devise_token_auth標準の仕組みに一本化する作業を進めています。<br>かなり影響範囲が広いため段階的に対応中です。

完了：<br>
・独自のリフレッシュ機構(RefreshToken等)を削除し、change_headers_on_each_request = true に戻した 
・フロント側のトークン自前管理ロジックを削除し、Cookieを中心とした構成への変更を進めた

検証・検討中：<br>
 ・change_headers_on_each_request = true に戻したことで発生しうる「バッチリクエスト問題」への対応(batch_request_buffer_throttleの調整) <br>
・LocalStorageへの依存を完全に断ち、Cookie ベースでの状態復元に置き換えられないか(devise_token_authのcookie_enabledモードへの移行を含めて検討)<br>

学習過程で生じた設計ミスですが、後から仕様を理解し直し、優先順位をつけて段階的に改善するプロセスとして捉えています。
